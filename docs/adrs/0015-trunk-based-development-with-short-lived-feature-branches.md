# Trunk-Based Development with One Short-Lived Branch per Feature

## Context and Problem Statement

The constitution says that each feature is developed on its own branch, but nothing limits how
large the feature on it may grow, says how the branch is kept in step with `main`, or says how
it is merged. A branch that is left alone while `main` moves is planned and built against a
state that no longer exists: it drifts from the API contract, the migrations, and the
architecture model on `main`, and it is reviewed as one large diff.

At the same time every merge to `main` publishes a container image
([ADR-0012](0012-container-images-published-to-ghcr.md)), and any commit on `main` can be
tagged as a release ([ADR-0007](0007-github-monorepo-for-backend-and-frontend.md)). `main`
therefore has to be releasable at every commit.

In this project most code is written by AI coding agents: once a feature is specified and
planned, its implementation takes minutes to hours, not weeks. What takes time is specifying
the feature — clarifying a spec can take days — and reviewing the result. A fixed limit on the
age of a branch would therefore cut into specification, not into coding.

The Merge gate of the constitution requires that a reviewer confirms the implementation
matches the spec, but nothing says who that reviewer is or who may merge. For the time being
the project has one developer. Pull requests are opened under that developer's GitHub account,
with code generated by AI coding agents, and GitHub does not let an account approve its own
pull request.

How does work reach `main`, how is a branch kept in step with `main` while it is open, who has
to approve it, and what does the history of `main` look like?

## Decision Drivers

* A feature is planned and implemented against the current `main`, not against the state of
  `main` when its spec was started.
* Every commit on `main` is releasable (ADR-0012).
* One linear history: no branch other than `main` has to be kept in sync, a release is a tag
  on `main`, and each commit on `main` is one reviewed change.
* Clarifying a spec takes as long as it takes; the workflow must not put a deadline on it.
* No change reaches `main` without a person having read and approved it. Code written by an
  agent is not checked by the agent that wrote it.
* The rules must be workable for a single developer whose account opens every pull request,
  and must not have to be redesigned when a second contributor joins.
* A pull request must be small enough to be reviewed against its spec. Review, not writing
  code, is the limiting step.
* The existing gates keep working as written: Principle III, the Merge gate, the checks of
  [ADR-0013](0013-openapi-spec-first-api-contract.md), and the scenario traceability check of
  [ADR-0014](0014-testing-strategy-by-layer.md) all treat a feature as merged in one piece.

## Considered Options

* Trunk-based development: one branch per feature, rebased onto `main` before planning and
  before implementation, reviewed, and merged complete as one squashed commit
* Trunk-based development: one branch per feature with a fixed limit on its age
* Trunk-based development: a feature merged in increments across several pull requests
* One branch per feature with no further rules
* GitFlow (`develop`, release branches, hotfix branches)

## Decision Outcome

Chosen option: "Trunk-based development: one branch per feature, rebased onto `main` before
planning and before implementation, reviewed, and merged complete as one squashed commit",
because the branch is brought up to date exactly where being out of date does harm — when the
design is made and when the code is written — without putting a deadline on specification. The
part of a feature's life that is exposed to drift, from implementation to merge, is short
because the code is generated. `main` gets one commit per feature, approved by a person, and contains only
complete features.

### Branching

* `main` is the trunk and the only long-lived branch. There is no `develop` branch and no
  release branch.
* Every change reaches `main` through a pull request from its own branch. Nothing is pushed to
  `main` directly, so the required status checks of
  [ADR-0008](0008-github-actions-for-continuous-integration.md) apply to every change.
* The age of a branch is not limited. A branch is kept short-lived by the size of its feature
  (see Features), not by a deadline.
* A release is a tag on a commit of `main` (ADR-0007, ADR-0012). A fix for a released version
  is made on `main` and released as a new version. Maintaining more than one released version
  would need release branches and is decided by a new ADR when it is needed.

### Keeping a branch in step with `main`

* A feature branch is rebased onto the current `main`:
  * before `speckit-plan`, so the plan is made against the current contract, migrations,
    architecture model, and ADRs;
  * before `speckit-implement`, so the code is written against the current code;
  * before it is merged, so the required status checks ran on what `main` will contain.
* If the rebase before `speckit-implement` brings in changes that affect the plan, the plan and
  the tasks are updated before implementation starts.
* A branch is brought up to date only by rebasing. `main` is not merged into a branch.
* A rebase is also where collisions in sequentially numbered artifacts are resolved: a feature
  number or a Flyway migration version that `main` has taken in the meantime is renumbered on
  the branch.
* A branch is rebased by the one who works on it and pushed with `--force-with-lease`. A branch
  belongs to one feature and is not shared as a base for other branches.

### Review

* Every pull request is reviewed and approved by a person before it is merged. This applies to
  every change, including changes that are exempt from the pipeline (Principle I).
* For a change written by an AI coding agent, the review is done by the developer on whose
  behalf the agent works. A review by an agent may be added to a pull request but does not
  count as the approval.
* Only a person merges a pull request. An agent may create the branch, push to it, and open the
  pull request under the developer's account; it MUST NOT merge the pull request, and
  auto-merge is not enabled.
* **While the project has one developer**, that developer reviews every pull request,
  including the ones opened under their own account, and merging the pull request is the
  approval. GitHub's required approving review is not switched on, because the account that
  opens a pull request cannot approve it.
* **Once the project has a second contributor**, the approval is given by a person who did not
  write the change and did not direct the agent that wrote it, and GitHub's required approving
  review is switched on. This needs no new ADR.
* The reviewer checks what the Merge gate asks of a reviewer: that the implementation matches
  the spec, and that the pull request violates no principle or constraint of the constitution
  without a recorded justification.
* The review covers what is merged. A change pushed after the approval is reviewed again,
  except a rebase onto `main` that needed no conflict resolution.

### Merging

* A pull request is merged only after it is reviewed and its required status checks pass.
* A pull request is merged by squashing: all commits of the branch become one commit on top of
  `main`. Merge commits and rebase-merges of individual commits are not used.
* The history of `main` is linear: one commit per pull request, each a complete feature or a
  complete exempt change.
* The branch is deleted when it is merged. Its individual commits remain visible in the pull
  request.

### Features

* A feature is developed on one branch and merged in one pull request, which contains its
  `spec.md`, `plan.md`, `tasks.md`, the implementation, and the tests of every acceptance
  scenario.
* A feature is merged complete. A pull request does not merge part of a feature, and `main`
  never contains a feature that is partly implemented.
* A feature is sized to be reviewable in one pull request. A feature that is not is split into
  smaller features, each with its own spec and each delivering working behaviour on its own.
  The split is made when the feature is specified or planned, not by merging it in parts.
* A change that is exempt from the pipeline (Principle I) follows the same branching and
  merging rules; it is rebased before it is merged.

### Consequences

* Good, because every commit on `main` is one complete feature or change, so every image
  published from `main` is releasable.
* Good, because a plan is never made, and code never written, against an outdated `main`.
* Good, because specification and clarification are not under a deadline.
* Good, because no commit is on `main` that a person has not read: agents do not merge, and
  everything goes through a pull request.
* Good, because the same rules carry over to a team; only the required approving review is
  switched on.
* Good, because the history of `main` is linear and reads as a list of features; a feature is
  reverted by reverting one commit, and `git bisect` lands on a feature.
* Good, because there is one branch to protect.
* Good, because Principle III, the Merge gate, the contract checks, and the scenario
  traceability check apply as they are written today.
* Neutral, because the branch for a feature is still created per feature, as Spec Kit expects.
* Neutral, because nothing limits how long a spec stays on its branch. A spec that is open for
  a long time costs only rebases until it is planned.
* Bad, because a feature's pull request carries the spec, the plan, the tasks, and the code at
  once. It is as large as the feature, and review quality depends on features being kept
  small.
* Bad, because every change, however small, waits for a person. With one developer, that
  person is the bottleneck for every merge.
* Bad, because while the project has one developer the review is not enforced by GitHub and
  leaves no approval record; that it happened rests on the developer's discipline and on
  agents not being allowed to merge.
* Bad, because a single developer reviews code produced at their own direction. There is no
  second pair of eyes until a second contributor joins.
* Bad, because squashing removes the branch's individual commits from `main`; the steps in
  which a feature was built can be read only in the pull request.
* Bad, because rebasing rewrites the branch and needs a forced push, and a branch that has
  waited long may need conflicts resolved at each rebase.
* Bad, because some work is hard to split into slices that each deliver working behaviour — a
  large migration, or a change that replaces existing behaviour across modules. Such work needs
  more effort at specification time.
* Bad, because the spec of a feature is not on `main` until the feature is; two features in
  progress cannot see each other's specs except on their branches.
* Bad, because the rebases before `speckit-plan` and `speckit-implement` and the size of a
  feature are not enforced by a tool.

### Confirmation

* The repository allows squash merging only; merge commits and rebase merging are disabled. It
  deletes branches on merge.
* Branch protection on `main` requires a pull request, the required status checks, a branch
  that is up to date with `main`, and a linear history. It rejects direct pushes and applies
  to administrators as well. No other long-lived branch exists.
* While the project has one developer, the number of required approving reviews is zero. It is
  set to one when a second contributor is given write access.
* Auto-merge is disabled in the repository settings. The instructions that agents work under
  state that an agent does not merge pull requests.
* The rebases before `speckit-plan` and `speckit-implement` are part of running those commands:
  the one who runs the command rebases first. Review of the pull request checks that the plan
  does not contradict what is on `main`.
* The scenario traceability check of ADR-0014 already fails a pull request that merges a spec
  whose scenarios have no tests, which is what a partly merged feature would look like.
* Review rejects a pull request that merges part of a feature.
* That a change pushed after the approval was reviewed again is checked by the reviewer before
  merging.
* At the Plan gate, a plan whose feature cannot be reviewed in one pull request is sent back to
  be split.

## Pros and Cons of the Options

### Trunk-based development, one branch per feature, rebased and squash-merged

* Good, because the branch is current at the two points where it matters, and `main` is always
  releasable.
* Good, because it changes nothing in the existing gates and checks.
* Good, because `main` has a linear history with one commit per feature, each merged by a
  person.
* Neutral, because it depends on implementation being fast, which holds while code is mostly
  generated from a reviewed spec and plan.
* Bad, because it forces features to be small and gives no way to merge a large one in parts.
* Bad, because a branch has no upper age, so nothing but the rebase rule keeps an old branch
  honest.

### Trunk-based development, one branch per feature with a fixed limit on its age

The same, but a branch must be merged within a fixed time, for example two working days of its
first commit.

* Good, because a hard limit keeps every branch close to `main` without relying on rebases.
* Bad, because the branch starts with the spec, and clarifying a spec can take longer than any
  limit that is short enough to be useful. The limit would be broken routinely or would push
  specification work off the branch.
* Bad, because the limit cannot be enforced by a tool and would depend on review.

### Trunk-based development, a feature merged in increments

A feature reaches `main` in several pull requests, each smaller than the feature.

* Good, because pull requests can be smaller than a feature, and a feature of any size can be
  integrated daily.
* Bad, because `main` then contains partly implemented features, so a commit on `main` is not
  releasable as it stands.
* Bad, because the checks of ADR-0013 and ADR-0014 would have to be adjusted for features that
  are merged but not finished.
* Bad, because it solves a problem — features too large for one pull request — that splitting
  the spec solves at lower cost here.

### One branch per feature with no further rules

The current wording of the constitution.

* Good, because `main` contains only finished features.
* Bad, because nothing stops a feature from growing, and the pull request is as large as the
  feature became.
* Bad, because nothing brings the branch up to date before the plan is made or the code is
  written, so it drifts from the contract, the migrations, and the architecture model on
  `main`.
* Bad, because the merge method is left open, so the history of `main` mixes merge commits and
  work-in-progress commits.
* Bad, because it does not say who reviews or who may merge, so an agent could merge its own
  work.

### GitFlow

* Good, because it supports several released versions maintained in parallel.
* Bad, because the project releases from one line and has no such need.
* Bad, because it adds a second long-lived branch and merges between branches, and delays
  integration.

* Trunk-based development: <https://trunkbaseddevelopment.com/>
* GitHub merge methods and linear history:
  <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github>
* Required reviews on GitHub:
  <https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#require-pull-request-reviews-before-merging>.
  GitHub does not let an account approve its own pull request, which is why the required
  approving review stays off while one developer's account opens every pull request.
  Opening agent pull requests under a separate identity (a bot account or a GitHub App) would
  allow the required review to be switched on earlier; that is not done now, to avoid
  maintaining a second identity for a solo project.
* Spec Kit does not tie a feature to its branch name in this repository: no branch-creating
  hook is configured in `.specify/extensions.yml`, and the commands find the feature directory
  through `.specify/feature.json`.
* The rebases could be made automatic with `before_plan` and `before_implement` hooks in
  `.specify/extensions.yml`. That is not decided here.
* Revisit this decision if features regularly cannot be split to fit one pull request, or if
  branches are regularly found to be out of date at review.
* Accepting this ADR requires amending the constitution:
  * Development Workflow and Quality Gates: "Each feature is developed on its own branch" is
    extended with the rules above — `main` as the only long-lived branch, no direct pushes,
    the rebase onto `main` before `speckit-plan`, before `speckit-implement`, and before
    merge, squash merging and a linear history on `main`, a feature merged complete in one
    pull request, and the split of a feature that does not fit. The Plan gate gains the size
    check. The Merge gate states that the reviewer is a person, that only a person merges a
    pull request, and that the required approving review is switched on once the project has
    a second contributor; the line on pipeline-exempt changes refers to the same review.
  * Principles I–V are unchanged.
